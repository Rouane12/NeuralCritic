# Neural Critic 200-capability status model

This document is the human-readable view of the 200-capability GameSpot benchmark. Milestone 1 classifies all 200 capabilities using repository, deterministic, browser, persistence, and operational evidence available on `2026-09-02`. It does **not** authorize implementation of missing or partial items.

The canonical machine-readable ledger is `docs/CAPABILITY_STATUS.csv`. It contains exactly 200 uniquely identified rows (`NC-GS-001` through `NC-GS-200`). `scripts/render_capability_ledger.py` regenerates the inventory tables below from that CSV; `scripts/audit_capability_ledger.py` enforces completeness, evidence references, status/level rules, dates, dependencies, risks, negative searches, and secret hygiene.

## Benchmark methodology

The benchmark behavior column normalizes observable reader journeys from the current public [GameSpot publication](https://www.gamespot.com/) and the broader maturity areas approved for the overhaul (editorial operations, persistence, security, analytics, and delivery). It is a comparison model, not a claim that Neural Critic should copy GameSpot's implementation or visual design. Each row asks whether Neural Critic provides the same class of outcome through its own existing architecture. The inventory was frozen at 20 domains × 10 stable capabilities so later milestones can update evidence/status without renumbering the benchmark.

## Status vocabulary

| Status | Meaning | Minimum evidence |
|---|---|---|
| ✅ Complete and verified | The entire applicable journey works at the expected product level. | The highest relevant evidence tier passes: an exact deterministic contract for fully static/generated artifacts, a real browser interaction for interactive surfaces, V4 for claimed persistence, or V5 for privileged/provider operations. |
| 🟡 Existing but partial / weaker / unverified | A substantial implementation exists, but the journey is incomplete, weaker than the benchmark, blocked from verification, or supported only by structural evidence. | File/route/data evidence plus a precise statement of what is missing or unverified. |
| ❌ Missing | No meaningful existing implementation was found after a documented architecture/code/data search. | Search scope and negative evidence are recorded. A missing visible control alone is insufficient if a backend/alternate surface may exist. |
| 🚫 Intentionally not required | Product owner explicitly decides the capability is out of scope. This is not a technical shortcut. | Decision, rationale, approver, date, and affected milestone are recorded. |

All 200 adopted rows must now carry one of these four statuses. Never default an uncertain row to ❌; use 🟡 and name the verification blocker unless a documented repository-wide negative search establishes absence.

## Verification levels

Use the highest level actually demonstrated:

| Level | Name | What it proves |
|---|---|---|
| V0 | Claim or observation only | A behavior was reported or casually observed, but ownership/source/runtime evidence is not recorded. V0 cannot support ✅, ❌, or 🚫. |
| V1 | Source inventory | Repository entry points, owners, data models, and dependencies were found, or a documented repository-wide search established absence. It does not prove integration/runtime behavior. |
| V2 | Deterministic integration | Repeatable static/build/unit-style checks prove wiring, schema/reference integrity, generated output, or exact live/generated data parity. It can fully verify a non-interactive artifact whose complete contract is deterministic. |
| V3 | Browser behavior | A real browser renders and exercises the relevant signed-out or non-persistent interaction with visible outcome and console/resource review where feasible. It does not prove a claimed server write survived reload. |
| V4 | Persisted state | The real authorized write succeeds, the source is re-read, UI state/count agrees, and reload or session resume preserves it; local-only preferences still require a reload check. |
| V5 | Production-equivalent operation | A privileged, provider, publication, or security-critical workflow succeeds end to end in production-equivalent conditions, including authorization/negative paths and cleanup where relevant. |

A capability normally needs V3 for ✅. A fully deterministic artifact such as generated canonical/schema/sitemap output can be ✅ at V2 when its whole contract is statically testable. Any capability that claims saved state, identity, community data, follows, preferences, or editorial state needs V4. Provider delivery, publishing, privileged operations, RLS/security, and similar operational capabilities need V5 or remain 🟡. Levels are evidence strength, not implementation progress: ❌ rows can be V1 because absence was proved only by source search.

## Classification workflow

For each capability:

1. Define the expected user journey without choosing a new implementation.
2. Search routes, templates, runtime modules, builders, migrations, Edge Functions, workflows, data, and existing audits.
3. Name the current owner(s) and dependencies. If two apparent owners exist, investigate the load/integration path before classifying.
4. Exercise deterministic contracts.
5. Exercise the real browser journey at representative desktop/mobile and light/dark states where applicable.
6. For writes, prove request success, source re-read, immediate UI update, reload persistence, authorization, and cleanup.
7. Record the highest verification level actually achieved.
8. Assign status from evidence. A blocked credentialed test is 🟡, not ✅.
9. Separate a product gap from a regression or pre-existing bug in `known_limitations`/`notes`.
10. Have another review confirm every ✅ or 🚫 before using the ledger for milestone planning.

## Evidence rules

Valid evidence is reproducible and close to the claim. Examples include:

- Exact audit/build/test command and exit status
- GitHub Actions workflow/run result for the exact commit
- Browser URL, viewport class, theme, auth state, visible result, console failures, and failed requests
- Real API/database operation category and source re-read (without tokens, credentials, private user data, or secret values)
- Reload result for any claimed persistence
- Negative authorization test for private/admin/security capabilities

The following are not sufficient by themselves:

- HTML exists
- A button or placeholder renders
- CSS looks correct in one viewport/theme
- JavaScript contains an event listener
- A Supabase table or migration exists
- An optimistic UI state changes before the request resolves
- A caught/suppressed error disappears from the console
- Mock/fake data produces a successful-looking interface

## Persistent-journey template

Use this sequence in the `journey` and `evidence` fields:

```text
trigger action
→ authorized real API/database write succeeds
→ UI state/count reflects confirmed result
→ source is queried again
→ page reloads or session resumes
→ state remains correct
→ unauthorized/conflicting action is rejected where relevant
```

For example, an article Like is not ✅ until the reaction write, exclusive state/count, re-read, and reload all agree for the authenticated user.

## Ledger quality gates

Before a capability audit is considered complete:

- The CSV contains exactly 200 IDs, with no duplicates or gaps.
- Every row defines benchmark behavior, Neural Critic equivalent, owner files, entry point, dependencies, and regression risk, or explicitly records that none were found after search.
- Every ✅ has sufficient verification level for its claim and reproducible evidence.
- Every 🟡 names the exact missing/weaker/unverified portion in `known_limitations`.
- Every ❌ records the search scope used to establish absence.
- Every 🚫 includes an explicit product decision and date.
- No row contains credentials, tokens, personal test data, or service-role/provider secrets.
- Changes to protected systems are cross-referenced to the regression matrix in `OVERHAUL_BASELINE.md`.
- Capability status changes and implementation changes are reviewed separately when practical.

## Change control

The ledger is an audit record, not a backlog generator. A 🟡 or ❌ row does not authorize implementation. Future milestones should select a bounded set of approved capabilities, identify existing owners, define regression scope, implement without duplication, and update status only after fresh evidence on the exact resulting commit. No capability is marked 🚫 in Milestone 1 because no explicit product-owner exclusion decision was supplied.
